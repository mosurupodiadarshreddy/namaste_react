Single Responsibility Principle (SRP) is a basic rule from Object-Oriented Programming.

👉 Definition = A function, class, or component should have only one responsibility (one job) and only one reason to change

🧠 Simple understanding

Think like this: “This piece of code should do only one thing, and do it well.”

❌ Wrong (violates SRP)
function userHandler() {
  fetchUserData();   // API work
  validateUser();    // validation
  saveToDB();        // database
  sendEmail();       // notification
}

👉 Problem:

Too many responsibilities
If email logic changes → this function changes
If DB changes → again same function changes
✅ Correct (follows SRP)
function fetchUser() {}
function validateUser() {}
function saveUser() {}
function sendEmail() {}

👉 Each function: Has one job , Changes independently

🔑 Key line to remember (for interviews)

“SRP means one unit of code should have only one reason to change.”

🔥 In React terms (quick)

One component → one purpose
Example:UserProfile → shows user info , UserPosts → shows posts

🔹 What is Modularity?

Modularity means breaking your code into small, independent, reusable pieces (modules).

Each module:Does one thing, Can be used anywhere, Can be changed without breaking others

🔹 How SRP connects to Modularity

From Object-Oriented Programming:

SRP says: one unit → one responsibility
Modularity says: build your system using many such small units

👉 So:

SRP = rule
Modularity = result/design style

❌ Without Modularity (Bad Code)
function handleUser() {
  const user = fetch("/api/user");  // API
  if (!user.name) throw Error();    // validation
  document.getElementById("name").innerText = user.name; // UI
}

🚨 Problems: Everything mixed together → Hard to test → Hard to reuse → One change breaks everything

✅ With Modularity (Using SRP)
function fetchUser() {
  return fetch("/api/user");
}

function validateUser(user) {
  if (!user.name) throw Error();
}

function displayUser(user) {
  document.getElementById("name").innerText = user.name;
}
async function handleUser() {
  const user = await fetchUser();
  validateUser(user);
  displayUser(user);
}

🔥 Why this is “good code”
1. Easy to understand

Each function name clearly tells what it does

2. Easy to change
API changes → only fetchUser
UI changes → only displayUser

3. Reusable
You can reuse validateUser() anywhere

4. Testable
You can test each function separately

🧠 Real-life analogy

Think of a restaurant kitchen:

One person cooks
One person serves
One person takes orders

👉 That’s modularity
👉 If one person does everything → chaos ❌

🔑 Final simple definition (interview ready)

Modularity is structuring code into small, independent units, each following SRP, so the code is easy to maintain, reuse, and scale.

🔹 Example to understand clearly

✔ Just a helper

✅ Custom Hook
import { useState, useEffect } from "react";

function useUser() {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch("/api/user")
      .then(res => res.json())
      .then(data => setUser(data));
  }, []);

  return user;
}

✔ Uses useState, useEffect
✔ Reusable across components
✔ This is a custom hook

🔹 Usage
function Profile() {
  const user = useUser();

  return <h1>{user?.name}</h1>;
}

Instead of writing API logic inside components:

  const user = useUser();

This follows SRP + modularity

🔴 The Problem: Large Single Bundle (Monolithic JS)

When you run your React app using Parcel, it takes all your code—components, hooks, utilities, and dependencies—and bundles everything into one (or a few) JavaScript files 📦. 
When you open the browser DevTools → Network → JS tab, you’ll notice a large .js file like main.js or index.js. In small apps this might be around 1 MB, but in large applications it can easily grow to 10–50 MB 🚨.

🧠 This happens because the bundler assumes:
👉 “The user might need everything, so let’s load everything upfront.”

So it includes all modules, even if they are not immediately needed—like grocery components ❌, restaurant pages ❌, admin panels ❌—everything gets bundled together ❌.

⚠️ This leads to serious problems. First, slow initial loading ⏳—the browser has to download, parse, and execute a large JS file before showing anything. 
👉 Bigger bundle = slower app startup. Second, wasted data 📉—for example,
 if a user opens only the Food page, the bundle still contains grocery logic, kitchen modules, and admin dashboard code, meaning a large portion (often ~80%) is unused initially. 
 Third, poor user experience 😓—users see a blank screen for longer, first paint is delayed, and performance suffers especially on slower networks or devices.

🔥 In real-world apps like Swiggy or Amazon, this doesn’t happen—they don’t load the entire application at once. When you open the home page, only the required code is loaded,
 not the seller dashboard or analytics pages.

❌ But without optimization, your current app behaves like this:
👉 App opens → Download 10MB bundle → Parse everything → Then show UI

🚨 In large-scale applications with multiple modules—Food 🍔, Grocery 🛒, Payments 💳, Profile 👤, Admin Panel ⚙️—all of this gets bundled into a single file, 
resulting in 15–50 MB bundles and very slow loading ❌.

🔑 Core Problem:
👉 All components are bundled into one large JavaScript file, causing slow initial load and unnecessary code download.

🧠 One important clarification: this is not just a Parcel issue. It’s actually a default bundling strategy problem.
 Tools like Webpack and Vite also bundle everything by default unless optimized.

🔥 Simple analogy to remember:
👉 You ordered one dish, but the restaurant delivered the entire kitchen menu 🍽️

📚 Definitions (clear + simple)
🔹 1. Code Splitting (MAIN CONCEPT)

Breaking a large bundle into smaller pieces (chunks)

👉 Example:
Instead of:

main.js (10MB)

You get:

home.js
food.js
grocery.js

✔ This is the base concept

🔹 2. Chunking

The actual process of creating those smaller pieces (chunks)

👉 Output of code splitting = chunks

So:

Code splitting → idea
Chunking → result
🔹 3. Lazy Loading

Loading a chunk only when it is needed

👉 Example:

User opens Home → load home.js
User clicks Grocery → then load grocery.js

✔ Most important term in React

🔹 4. Dynamic Bundling

Creating bundles dynamically based on usage (at runtime or build time)

👉 Instead of one fixed bundle:

Different bundles load based on user navigation
🔹 5. On-Demand Loading

Loading code only when the user requests it

👉 Same idea as lazy loading
Just different wording

🔹 6. On Import Loading

Loading code when a dynamic import is executed

import("./Grocery");

👉 When this line runs → that chunk loads

✔ This is how lazy loading works internally

🔥 Relationship (very important)
Code Splitting (concept)
        ↓
Chunking (creating pieces)
        ↓
Lazy Loading / On-Demand Loading (when to load)
        ↓
Dynamic Import (how to trigger loading)
🔑 Final understanding
✔ Code Splitting = breaking code
✔ Chunks = smaller files
✔ Lazy Loading = loading when needed
✔ Others = similar terms / implementation details
🧠 Interview one-liner

“Code splitting divides a large bundle into smaller chunks, and lazy loading ensures those chunks are loaded only when required using dynamic imports.”

🧠 Why we need Suspense

When you use:

const Grocery = lazy(() => import("./Grocery"));

👉 What happens:

App loads → main bundle loads ✅
Grocery is NOT loaded ❌
User clicks /grocery
React triggers dynamic import
Browser starts downloading grocery.chunk.js ⏳

👉 During this time:

React is waiting for the component
UI has nothing to show yet

✔ Correct ✅
But instead of “breaking”, it’s better to say:

👉 “There is a loading state where component is not yet available”

🔴 Problem without Suspense
User clicks Grocery →
Component not loaded yet →
Blank screen 😶
✅ Solution: Suspense

From React:

Suspense is a component that lets you show a fallback UI while waiting for something to load

🔹 Simple definition

Suspense handles the loading state of lazy components

🔹 How to use it
import { lazy, Suspense } from "react";

const Grocery = lazy(() => import("./src/components/Grocery"));

Now wrap it:

{
  path: "/grocery",
  element: (
    <Suspense fallback={<h1>Loading Grocery...</h1>}>
      <Grocery />
    </Suspense>
  )
}
🔥 What happens now

When user clicks /grocery:

React tries to render <Grocery />
It’s not loaded yet ❌
Suspense shows fallback:
<h1>Loading Grocery...</h1>
Once loaded → Grocery renders ✅
⚡ Real flow
Click Grocery →
Show fallback UI →
Load chunk →
Render component
🔹 Where do we get Suspense?

👉 From React itself:

import { Suspense } from "react";
🔹 Best practice (important)

Instead of text, use your Shimmer UI

<Suspense fallback={<Shimmer />}>
  <Grocery />
</Suspense>
🔑 Final understanding
Lazy → delays loading component
Suspense → handles loading UI

“Suspense is used with React.lazy to display a fallback UI while the lazy-loaded component is being fetched asynchronously.”
